01Project Overview▼

🚀 Project Name

AI-Based Resume Screening and Ranking System (also called Resume Matcher)

FastAPIReact 18PostgreSQL Sentence-TransformersSQLAlchemy ORMVite

⏱ Elevator Pitch (30 seconds)

This is a full-stack web application that helps HR professionals screen and rank resumes against job descriptions using AI. It extracts skills from uploaded resumes, computes semantic similarity using a transformer-based NLP model (all-MiniLM-L6-v2), and produces a weighted ranking combining both skill-match and semantic scores. HR users get a rich dashboard with charts to compare and shortlist candidates automatically.

📝 1-Minute Explanation

The system has two user roles: HR and Candidate. HR users create job postings with required skills, then upload candidate resumes (.docx files). The backend extracts text from resumes, detects skills using case-insensitive keyword matching against a canonical skills database, and generates 384-dimensional sentence embeddings using the all-MiniLM-L6-v2 model. When HR triggers "Generate Rankings", the system computes a final score = 0.7 × semantic_similarity + 0.3 × skill_overlap, then auto-classifies candidates as "Accepted" (score ≥ 0.6) or "Rejected". The React frontend displays results with Bar, Doughnut, Scatter, Line, and Radar charts for visual analysis. Candidates log in to browse jobs and upload their own resumes.

📝 3-Minute Explanation

This project solves the problem of manual resume screening in recruitment. Traditional hiring requires HR professionals to read hundreds of resumes, which is slow, biased, and inconsistent. Our system automates this with two AI techniques:

  1. Skill-based matching: The system maintains a skills table. When a resume is uploaded, it detects which skills appear in the text using case-insensitive substring matching and computes what percentage of required job skills the candidate possesses.
  2. Semantic matching: Both the job description and resume text are converted into 384-dimensional numerical vectors using the Sentence-Transformers library (all-MiniLM-L6-v2). Cosine similarity between these vectors captures meaning beyond exact keyword matches — e.g., "machine learning" and "deep learning" would have high similarity even without exact overlap.

The final score is a weighted combination: final = 0.7 × semantic + 0.3 × skill_overlap. Candidates with a score ≥ 0.6 are auto-accepted; below that, auto-rejected. The frontend dashboard shows multiple charts: a Bar chart for skill coverage, a Doughnut chart for candidate quality distribution, a Scatter plot of semantic vs skill scores, Line charts for per-skill presence, and Radar charts in the candidate detail modal. HR can compare multiple candidates side-by-side. Authentication uses bcrypt password hashing via Passlib.

📝 5-Minute Explanation

Add the following depth to the 3-minute version:

  • Database Design: 7 tables — users, candidates, resumes, skills, resume_skills, jobs, job_skills, rankings. The schema follows 3NF with proper foreign keys and cascade deletes. Many-to-many relationships exist between resumes↔skills and jobs↔skills via junction tables.
  • API Layer: FastAPI provides 10+ REST endpoints. Form data (not JSON) is used for uploads and job creation. Pydantic schemas validate request/response structures. CORS middleware allows cross-origin requests from the Vite dev server (port 5173 → 8000).
  • Frontend Architecture: React 18 with React Router v6 for client-side routing. Two role-based views: HR Dashboard (with charts, ranking, comparison modal) and Candidate Page (view jobs + upload resume). State managed via React's built-in useState/useEffect hooks. Session persisted in localStorage (role, user_id, name).
  • ML Pipeline: On upload → extract text (python-docx) → parse contacts (regex) → detect skills (substring match) → generate embedding (SentenceTransformer) → store in JSONB column → rank on demand using cosine similarity + skill overlap → auto-shortlist.
  • Security: bcrypt password hashing, email regex validation, old password auto-migration to hashed form, role-based route guards (HR sees only own jobs), CORS config. No JWT — session via localStorage.

🎓 Interviewer's Perspective

Q: Why FastAPI over Flask?
A: FastAPI provides automatic request validation via Pydantic, auto-generated Swagger docs at /docs, native async support, and significantly better performance. Flask requires manual validation and doesn't have built-in schema support.

🎓 Interviewer's Perspective

Q: Why PostgreSQL over MongoDB?
A: Our data is highly relational (candidates → resumes → skills with many-to-many relationships). PostgreSQL's JSONB columns let us store embeddings (semi-structured) while keeping relational integrity for foreign keys and constraints. MongoDB would sacrifice ACID compliance and relational queries.

06AI / Machine Learning▼

🧠 Model: all-MiniLM-L6-v2

A pre-trained Sentence Transformer model from Hugging Face. It converts any text into a 384-dimensional dense vector (embedding) that captures semantic meaning.

Property Value
Architecture MiniLM (distilled BERT variant)
Output Dimension 384 floats
Max Sequence Length 256 tokens
Training Data 1B+ sentence pairs (NLI, paraphrases)
Use Case Semantic similarity, search, clustering
Stored As JSONB column in PostgreSQL

📐 Cosine Similarity

Measures the angle between two vectors. Range: [-1, 1]. In this project, it's normalized to [0, 1] using (cosine_sim + 1) / 2. 

def cosine_sim(a, b):
    a = np.array(a, dtype=float)
    b = np.array(b, dtype=float)
    denom = np.linalg.norm(a) * np.linalg.norm(b)
    if denom == 0: return 0.0
    return float(np.dot(a, b) / denom)

⚖️ Final Score Formula

# With embeddings (compute_final_score):
semantic = (cosine_sim(job_emb, resume_emb) + 1) / 2   # normalize to 0–1
skill = matched_skills / total_job_skills               # fraction overlap
final_score = 0.7 * semantic + 0.3 * skill

# In summary endpoint (slightly different weights):
final = 0.8 * skill_score + 0.2 * semantic
if skill_score > 0.7: final += 0.05   # bonus boost

# Auto-shortlisting threshold:
status = "accepted" if final_score >= 0.6 else "rejected"

🔍 Skill Extraction

Uses case-insensitive substring matching against the canonical skills database. Not ML-based — purely pattern matching.

def extract_skills(text, canonical_skills):
    found = []
    low = (text or "").lower()
    for s in canonical_skills:
        if s.lower() in low:
            found.append((s, 0.95))   # fixed confidence
    return deduplicated(found)
⚠️ Limitation

Substring matching can produce false positives — e.g., "java" matches "javascript". A better approach would use NER (spaCy) or regex word boundaries.

📊 Embedding Fallback

If sentence-transformers fails to load, embed_text() returns a deterministic pseudo-vector from hash(text) so the system still runs (degraded but functional).

ML Interview Questions

Question Answer Priority
What is a sentence embedding? A fixed-length numerical vector that captures the semantic meaning of a sentence. Similar sentences have similar vectors. 🟢
Why cosine similarity over Euclidean distance? Cosine measures angle (direction), which is more meaningful for high-dimensional sparse embeddings. Euclidean measures magnitude, which is less informative for text. 🟢
What is transfer learning? Using a model pre-trained on a large dataset (like all-MiniLM-L6-v2) and applying it to a new task without retraining. We use it to get embeddings without training our own model. 🟢
Why all-MiniLM-L6-v2 specifically? It's compact (22MB), fast, and produces good 384-dim embeddings. It's a distilled version of larger BERT models — excellent tradeoff between speed and quality. 🟡
What's the difference between TF-IDF and sentence embeddings? TF-IDF is bag-of-words based — it counts word frequency but ignores word order and meaning. Sentence embeddings capture context, synonyms, and semantic relationships. 🟢

Not Used in This Project

  • Fine-Tuning: The model is used as-is (inference only), no fine-tuning on custom data.
  • RAG (Retrieval Augmented Generation): Not used — no LLM or generation component.
  • Classification/Regression models: No supervised learning — ranking is formula-based.
  • CNN/Transformer training: No model training — only pre-trained inference.
  • Confusion Matrix/Precision/Recall: No evaluation metrics computed — no labeled test set.

ER Diagram (SVG)

JSONB Usage

PostgreSQL's JSONB type stores embeddings (384-float arrays) and parsed resume data (name, email, skills). JSONB allows indexing and querying inside JSON structures while keeping the relational model intact.

💡 Tip

JSONB is chosen over JSON because it's stored in binary format — faster to query, supports indexing (GIN), and strips duplicates/whitespace.

DB Interview Questions

Question Answer
Why JSONB for embeddings? Embeddings are variable-length float arrays. JSONB allows storing them without creating a separate table with 384 columns. It's queryable and supports GIN indexing.
What is the unique constraint on rankings? UNIQUE(job_id, resume_id) prevents duplicate rankings for the same resume-job pair.
Why ON DELETE CASCADE? When a parent record (e.g., candidate) is deleted, all child records (resumes, resume_skills) are automatically deleted to maintain referential integrity.
Normalization level? 3NF — no transitive dependencies. Junction tables (resume_skills, job_skills) properly handle M:M relationships.

ℹ️ Important

No JWT tokens are used. Session is maintained via localStorage on the client. Role and user_id are sent as query parameters on every protected API call. This is not production-secure.

Authorization

Role-based access enforced in backend:

  • HR users can only see their own jobs (Job.created_by == user_id)
  • Job summary/rankings check role == "hr" && job.created_by != user_id → 403
  • Candidates see all jobs but cannot create jobs
  • Manual status update endpoint is disabled (returns 403)

Dependency Injection: get_db()

def get_db():
    db = SessionLocal()
    try:
        yield db          # FastAPI injects this into route handler
    finally:
        db.close()       # ensures session is always closed

# Used as: db: Session = Depends(get_db)
💡 Tip

FastAPI's Depends() is similar to dependency injection in Spring — it automatically creates, injects, and disposes database sessions per request.

Error Handling

Errors raised via HTTPException(status_code, detail). Common codes:

  • 400: Bad request (invalid email, weak password, duplicate user)
  • 401: Unauthorized (wrong credentials)
  • 403: Forbidden (wrong owner, manual status disabled)
  • 404: Not found (job/resume missing)

Startup Logic

When the server starts: Base.metadata.create_all(bind=engine) creates all tables if they don't exist, and _normalize_and_merge_skills_table() deduplicates skills by merging case variants.

⚠️ Password Migration Risk

The login endpoint supports old plain-text passwords via a fallback comparison (stored == password). This means if a password was stored in plain text (legacy), it will still work but gets auto-migrated to bcrypt on login. However, the plain-text comparison is a security concern.

Bottlenecks

  • Ranking computation: O(resumes × skills) per job — slow for thousands of resumes. Solution: batch processing with Celery.
  • Embedding generation: SentenceTransformer encode() is CPU-intensive. Solution: GPU inference or pre-computed embeddings.
  • JSONB cosine similarity: Not indexed for approximate nearest neighbor. Solution: pgvector extension or dedicated vector DB.

19TCS Interview Questions (40)▼
  1. Q: What is FastAPI? A: Modern Python web framework for building REST APIs with auto validation, async support, and auto-generated Swagger docs.
  2. Q: What is an ORM? A: Object-Relational Mapper translates Python objects to SQL tables. We use SQLAlchemy — e.g., db.query(Job).all() instead of SELECT * FROM jobs.
  3. Q: What is cosine similarity? A: Measures the cosine of the angle between two vectors. Range [-1,1]. Similar texts produce vectors pointing in the same direction.
  4. Q: Why PostgreSQL JSONB? A: Stores 384-float embedding arrays and parsed JSON without separate tables. JSONB supports indexing and binary storage.
  5. Q: What is bcrypt? A: Adaptive hash function with salt. Resistant to rainbow table attacks. Used via Passlib for password hashing.
  6. Q: What is React's useState? A: Hook that lets functional components hold state. Returns [value, setter]. Triggers re-render when updated.
  7. Q: What is Axios? A: Promise-based HTTP client. We use it with interceptors and upload progress tracking.
  8. Q: What is CORS? A: Cross-Origin Resource Sharing — browser security that blocks frontend (port 5173) from calling backend (port 8000) unless allowed. We set allow_origins=["*"].
  9. Q: What is Pydantic? A: Data validation library used by FastAPI. Schemas in schemas.py define what request/response data looks like.
  10. Q: What is Vite? A: Modern build tool that uses ES modules for fast hot-reload. Replaces older tools like Webpack/CRA.
  11. Q: What is useEffect? A: React hook for side effects (API calls, subscriptions). Runs after component renders. [] dependency = runs once on mount.
  12. Q: How do you handle file uploads? A: FormData on frontend → multipart/form-data POST → FastAPI UploadFile → shutil.copyfileobj to disk → extract text.
  13. Q: What is a foreign key? A: A column referencing another table's primary key. E.g., resumes.candidate_id → candidates.candidate_id.
  14. Q: What is CASCADE DELETE? A: When parent is deleted, all children are auto-deleted. Used on resumes → resume_skills.
  15. Q: What is a junction table? A: Intermediate table for M:M relationships. resume_skills connects resumes and skills.
  16. Q: What is embedding? A: Numerical vector representing text meaning. "Python developer" → [0.12, -0.34, ...] (384 numbers).
  17. Q: What is transfer learning? A: Using a pre-trained model (all-MiniLM-L6-v2 trained on 1B+ sentences) for our task without retraining.
  18. Q: What is Chart.js? A: JavaScript library for rendering charts. We use react-chartjs-2 wrapper for React integration.
  19. Q: How is authentication done? A: bcrypt hashing on register, verify on login, store role/user_id in localStorage. No JWT.
  20. Q: What is React Router? A: Library for client-side routing in React. Maps URLs to components without page reload.
  21. Q: What is ASGI? A: Async Server Gateway Interface — protocol for Python async web apps. Uvicorn implements it.
  22. Q: What are CSS variables? A: Custom properties like --accent: #2563eb defined in :root. Used with var(--accent) for consistent theming.
  23. Q: What is dependency injection? A: Design pattern where dependencies are provided externally. FastAPI's Depends(get_db) injects database sessions.
  24. Q: Why .docx not PDF? A: python-docx reliably extracts text from .docx. PDF extraction (PyPDF2/pdfplumber) is harder due to layout complexity.
  25. Q: What is the scoring threshold? A: 0.6 — candidates scoring ≥ 0.6 are auto-accepted, below are auto-rejected.
  26. Q: How do you prevent duplicate skills? A: _normalize_and_merge_skills_table() runs at startup, lowercasing all skill names and merging duplicates.
  27. Q: What is useMemo? A: React hook that memoizes expensive computations. Recalculates only when dependencies change.
  28. Q: What is the env file? A: Stores environment variables (DATABASE_URL, UPLOAD_DIR). Loaded by python-dotenv. Keeps secrets out of code.
  29. Q: What database driver does SQLAlchemy use? A: psycopg2-binary — the most popular PostgreSQL adapter for Python.
  30. Q: How does the compare feature work? A: HR selects multiple candidates → CompareModal fetches summary → shows side-by-side radar charts and stacked bar chart.
  31. Q: What is the virtual DOM? A: React's in-memory representation of the actual DOM. React diffs virtual DOM changes and updates only what changed (reconciliation).
  32. Q: What is normalization in databases? A: Organizing data to reduce redundancy. Our schema is in 3NF — no transitive dependencies.
  33. Q: How is role-based access enforced? A: Backend checks: if role=="hr" and job.created_by != user_id → 403 Forbidden.
  34. Q: What is semantic similarity? A: Measuring meaning-based closeness between texts using embeddings, not just keyword overlap.
  35. Q: What is the difference between GET and POST? A: GET retrieves data (idempotent). POST creates/modifies data (non-idempotent). We use POST for uploads and creation.
  36. Q: What happens if the ML model fails to load? A: embed_text() falls back to a deterministic hash-based pseudo-vector. The system still works but with degraded accuracy.
  37. Q: What is a Radar chart? A: Displays multivariate data on axes starting from the center. We use it to show which job skills a candidate has vs doesn't have.
  38. Q: What is react-toastify? A: Library for showing toast notifications (success/error pop-ups) in React apps.
  39. Q: How do you handle errors in API calls? A: try/catch around axios calls, extract error.response.data.detail, show via toast.error().
  40. Q: What is the project's database connection string format? A: postgresql://username:password@host:port/dbname

23Difficult Cross Questions + Defense▼
Tough Question Defense Answer
Your skill matching is just string matching — is that really AI? The skill matching is one component. The AI part is the sentence-transformer embeddings that capture semantic meaning. The system combines both approaches for a more robust ranking. The substring matching is a practical engineering choice that works well for known skill taxonomies.
Why no JWT? localStorage isn't secure. You're right — localStorage is vulnerable to XSS. For this prototype/academic project, it simplifies the flow. In production, I would implement JWT with HTTP-only cookies and refresh token rotation.
The scoring weights are hardcoded — isn't that biased? The 0.7/0.3 split was chosen empirically. In a production system, I'd make these configurable per job or use learning-to-rank algorithms to optimize weights from HR feedback.
CORS * allows any origin — isn't that a security hole? Yes, in production I would whitelist only the frontend domain. The wildcard is for local development convenience where frontend and backend run on different ports.
What if two candidates have the same score? Currently, ties are broken by database insertion order (essentially arbitrary). A better approach would be secondary sorting by coverage_percent or semantic score.
"java" in "javascript" — your skill matching has false positives. Acknowledged limitation. Word-boundary regex (\bjava\b) or NLP-based NER (spaCy) would fix this. For this prototype, the canonical skills list mitigates it since HR defines specific expected skills.
Why two different scoring formulas in rank and summary? The rank endpoint uses compute_final_score (0.7 semantic + 0.3 skill) when embeddings are available. The summary endpoint recalculates with a different weight (0.8 skill + 0.2 semantic + bonus) for display consistency. This should ideally be unified.
No tests at all — how do you know it works? Tested manually using the 43 .docx resumes in the uploads directory and the Swagger UI. I'd add pytest + React Testing Library for automated coverage in production.
