1.1 What the project is

Names you will see

  • UI brand: "TalentFlow ATS" (index.html:9). ATS = Applicant Tracking System.
  • API title: "AI Resume Screening & Matching Engine", version 2.3.0 (main.py:139–144).
  • GitHub remote: pratyushkandari/ai-resume-screening-platform (from .git/config).

Problem it addresses

Recruiters receive many resumes per opening. Reading each one is slow. Plain keyword search misses context, and sending every resume to a large language model is expensive and non-deterministic. This project scores each resume against a job using two signals: which required skills appear (exact keyword matching) and how semantically similar the whole resume is to the job text (sentence embeddings). It then ranks the candidates and shows them on a dashboard.

1.2 Executive summary & technical summary

In plain language

An HR user posts a job and lists required skills, for example "python, docker, pytorch". Candidates upload resumes. The server reads the text out of each file, finds the candidate's name, email and phone with pattern matching, and looks for the job's skills in the text. It also turns both the job description and the resume into a list of 384 numbers that capture meaning (an embedding). The closer two embeddings point in the same direction, the more similar the texts. Each candidate gets a score: 70% from the share of required skills found, 30% from text similarity, and a +0.05 bonus if they cover at least 70% of the skills. Scores of 0.60 or higher are labelled "accepted" (the UI shows "Shortlisted"). The rest are "rejected" (the UI shows "Under Review").

Technically

  • Backend: a single FastAPI app (backend/app/main.py, 1,074 lines) with 15 HTTP routes. It uses SQLAlchemy ORM on PostgreSQL (SQLite in tests), PyJWT bearer tokens with bcrypt password hashes, and an optional Redis cache-aside layer for the dashboard summary Implemented.
  • ML: sentence-transformers/all-MiniLM-L6-v2 loaded lazily for inference only (no training, no LLM, no RAG). Embeddings are stored as JSON arrays in the database. Scoring uses NumPy cosine similarity plus Python set intersection for skills Implemented. If the model can't load, a random vector is used instead, which makes semantic scores meaningless (section E).
  • Frontend: a React 18 single-page app (Vite build, React Router, Axios, Chart.js) with role-based screens. The JWT is stored in localStorage Implemented.
  • Quality and ops: 29 pytest tests (all passed here) Verified by execution. There are Docker/Compose, Nginx, Kubernetes, Render and Vercel configs plus a GitHub Actions workflow Configured. None of these deployments could be verified.

1.3 Interview explanations (honest, verified versions)

RuleEvery sentence below is supported by code you can show. Avoid the README's throughput numbers unless you can explain how they were measured and what they exclude (see H3).
30-second version

"I built an AI-assisted resume screening app. Recruiters post a job with required skills, and candidates upload resumes as PDF, Word or text. A FastAPI backend extracts the text and detects skills with word-boundary regex. It also embeds both the job and the resume with a pretrained MiniLM sentence-transformer. Each candidate gets a composite score: 70% skill overlap, 30% semantic similarity. The React dashboard ranks candidates and shows skill gaps with charts. It uses PostgreSQL through SQLAlchemy and JWT authentication, and it has a 29-test pytest suite."

2-minute version

Problem. Screening many resumes by hand is slow. Keyword search is brittle. Calling an LLM per resume is costly and non-deterministic.

Design. React SPA → FastAPI → PostgreSQL. On upload, I stream the file to disk with a 15 MB cap and extract text (pypdf / python-docx). I parse contacts with regex and match skills from a skills table using word-boundary regex, so "r" doesn't match inside "programming". I compute a 384-dimension MiniLM embedding and store everything relationally: candidates, resumes, skills, resume_skills, jobs, job_skills, rankings, users.

Scoring. Skill overlap = matched required skills ÷ required skills. Semantic score = cosine similarity rescaled from [-1, 1] to [0, 1]. Final = min(1, 0.7·skill + 0.3·semantic + 0.05 bonus if skill ≥ 0.7). The threshold is 0.6. Ranking stacks all resume vectors into a NumPy matrix and computes the cosines in one matrix-vector product.

Engineering. JWT plus bcrypt auth with two roles, an optional Redis cache for the dashboard summary with invalidation on upload, request-ID and latency middleware, /healthz, /readyz and /metrics endpoints, Docker Compose, and a CI workflow running the tests.

Honest limits. No labelled dataset, so I can't claim accuracy. The weights 0.7/0.3 are hand-picked. Skill matching misses synonyms. I'd fix the authorization checks and the N+1 queries next.

5-minute version (structure + talking points)

  6. What you'd improve (30s): enforce require_role and ownership on every HR route, remove the query-parameter role fallback, protect downloads, batch the DB queries, move embedding to a background worker, evaluate ranking quality with labelled data.

1.5 High-level architecture

Primary execution flow in one paragraph

A candidate uploads a file. upload_resume streams it to UPLOAD_DIR and calls _process_single_resume_file, which extracts text, parses contacts, upserts a Candidate by email, creates a Resume with its embedding, detects skills against the skills table, writes resume_skills rows, and invalidates the cached summary. Later the recruiter opens the dashboard. GET /api/jobs/{id}/summary loads all resumes linked to that job, scores each one with calculate_candidate_match, keeps each candidate's best resume, adds chart aggregates, caches the result in Redis (if available) and returns it. Pressing "Evaluate Candidates" calls POST /rank, which recomputes scores in a vectorized way, replaces the rows in rankings, and the UI then re-fetches the summary.

1.6 Prerequisites, setup and startup (derived from repo files)

Two setup traps found by running it
  1. SQLAlchemy 2.1 breaks import. requirements.txt says sqlalchemy>=2.0.0. A fresh install today pulls 2.1.x, whose default PostgreSQL driver is psycopg (v3). The repo installs psycopg2-binary, so importing app.db fails with ModuleNotFoundError: No module named 'psycopg' Verified by execution. Fix: pin sqlalchemy<2.1 or use the URL scheme postgresql+psycopg2:// or install psycopg[binary].
  2. The embedding model downloads at first use. all-MiniLM-L6-v2 is fetched from the Hugging Face Hub on the first embed call. Without network access the app silently falls back to random vectors (/readyz reports "ml_model": "fallback_mode") Verified by execution.

B. Architecture and system workflow

What "architecture" means here

Core understandingArchitecture is the set of big parts of a system, what each is responsible for, and how they talk. Think of a restaurant: the dining room (frontend) takes orders, the kitchen (backend) cooks, the pantry (database) stores ingredients, and a recipe book (the ML model) guides how dishes are judged.
In this repositoryA classic three-tier web app: React SPA (presentation) → FastAPI monolith (application/business logic in main.py + helpers in ml_utils.py/auth.py) → PostgreSQL (data). Redis is an optional side-cache. The ML model runs in-process inside the API (no separate inference service). Communication is synchronous HTTP/JSON. There are no message queues, background jobs or service-to-service calls.
Interview extensionIt is a modular monolith in spirit but mostly a single module. A "layered" refactor would introduce routers (APIRouter per domain), a service layer (scoring and ingestion orchestration), and a repository/data-access layer. That makes unit testing and swapping storage (for example, moving to pgvector) easier. The in-process model couples API latency and memory to ML inference; at scale you separate them (section F.4).

B.1 Startup sequence (what happens on uvicorn app.main:app)

  1. Python imports app.main, which imports app.db: load_dotenv() reads .env; create_engine(...) builds a connection pool (no connection yet, but the driver module is imported) db.py:9–26.
  2. app.models registers 8 tables on Base.metadata. app.ml_utils imports NumPy, python-docx and pypdf. The model is not loaded yet (lazy) ml_utils.py:9–35.
  3. app.cache tries to connect to Redis and PINGs once. The result is frozen in REDIS_AVAILABLE for the process lifetime cache.py:18–28.
  4. app.auth reads JWT_SECRET_KEY (or uses the hard-coded fallback).
  5. Module-level: logging.basicConfig, os.makedirs(UPLOAD_DIR), a ThreadPoolExecutor that is never used, and the METRICS dict main.py:45–67.
  6. FastAPI app created with the lifespan handler; CORS and the trace middleware registered; routes registered by decorators.
  7. Uvicorn starts serving and runs the lifespan startup: Base.metadata.create_all (creates missing tables only, never alters existing ones), then _normalize_and_merge_skills_table(). B.2 Request lifecycle (generic)

  1. Browser: Axios builds the request. The interceptor adds Authorization: Bearer <token> if one is in localStorage api.js:17–26.
  2. Proxy: Vite dev server (dev) or Nginx (Docker) forwards /api/* to the backend on port 8000 nginx.conf:38–48.
  3. Middleware: CORS, then trace_and_log_requests: increments counters, assigns a request ID, awaits the handler, sets X-Request-ID and X-Response-Time-MS, and logs main.py:158–180.
  4. Routing and validation: FastAPI matches the path, parses path, query and form parameters (invalid types → automatic 422).
  5. Dependencies: get_db opens a session. get_optional_user/get_current_user decode the JWT and load the user.
  6. Handler: business logic, ORM queries and commits, maybe ML calls. Sync (def) handlers run in a worker thread pool; async def handlers run on the event loop.
  7. Response: response_model validates and serializes. The get_db finally closes the session. HTTPExceptions become JSON {"detail": ...} with the right status code.
  8. Browser: the response interceptor handles a 401 by clearing localStorage and redirecting to "/" api.js:29–41.

B.3 End-to-end user journeys

J1 · Register & login
  1. Login.jsx validates email/password locally and POSTs JSON to /api/register with the chosen role Login.jsx:79–91.
  2. register parses JSON or form data, sanitizes the name, validates email and password, coerces any unknown role to "candidate" (but accepts "hr" from anyone), checks for a duplicate email case-insensitively, hashes with bcrypt, commits, and returns a JWT main.py:273–351.
  3. The UI stores the returned token but doesn't set a role, so it still shows the sign-in form with a success message. /api/login verifies the password (or migrates a legacy plaintext one) and returns a token plus role, name and user_id main.py:363–416.
  4. The UI stores token, role, user_id, name in localStorage and calls setRole, which re-renders App into the role's routes Login.jsx:97–111.

J2 · HR posts a job

  2. create_job resolves the effective user: the token user, or the user whose id is in created_by if there is no token. It requires role == "hr" main.py:479–487.
  3. Validates title (3–120) and description (20–10,000), cleans skills (lowercase, allowed chars, ≤50 chars, dedupe) main.py:489–521.
  4. Embeds title + "\n" + description (skills are not part of the embedding), commits the job, then upserts each skill into skills and links it via job_skills main.py:523–553.

J3 · Candidate uploads resume(s) — the ingestion pipeline
  1. UploadResume.jsx checks extension, size and emptiness client-side. One file → POST /api/resumes/upload with file; several → POST /api/resumes/batch-upload with files; job_id is optional UploadResume.jsx:101–126.

  6. Skill detection: load all skill names, run extract_skills, upsert links into resume_skills with confidence 0.95, update parsed_json.skills main.py:636–662.

J4 · HR dashboard, evaluation and ranking

FastAPI (+ Starlette, Pydantic, Uvicorn)

Core understandingA Python web framework. You write functions and decorate them with @app.get("/path"). FastAPI turns HTTP requests into function calls and return values into JSON. Type hints drive validation and automatic API docs (/docs). Uvicorn is the server program that listens on a port and speaks the ASGI protocol to FastAPI.
In this repositoryOne FastAPI instance with a lifespan handler main.py:139–144. It uses Depends for DB sessions and auth, Form/File/UploadFile for multipart, Query(ge=1, le=100) for pagination bounds main.py:438–439, response_model for output shapes, and HTTPException for errors. register/login read the raw Request to accept both JSON and form bodies main.py:283–291.
Interview extensionWhy FastAPI: async-capable, typed, automatic OpenAPI, and a natural fit for Python ML code. Sync vs async: def routes run in a thread pool; async def routes run on the event loop, and blocking calls inside them stall all requests (this happens here with bcrypt, measured in H3). Alternatives: Flask (simpler, sync, no built-in validation), Django + DRF (batteries-included ORM/admin/auth, heavier), Node/Express (would split ML into a separate Python service). Switching to Flask would mean adding marshmallow/pydantic manually and losing auto-docs. Switching to Django gives migrations and an admin for free but means rewriting models.

SQLAlchemy ORM + PostgreSQL (SQLite in tests)

Core understandingA relational database stores data in tables with rows and columns, linked by keys. An ORM (Object-Relational Mapper) lets you work with Python classes (Candidate, Resume) instead of writing SQL strings. PostgreSQL is a production-grade open-source database. SQLite is a file or in-memory database that is handy for tests.
In this repositoryEngine with a connection pool db.py:18–23. 8 declarative models, foreign keys with ondelete rules, relationships with cascades models.py:27–31. Schema creation via create_all at startup (no migrations). JSON columns that become JSONB on PostgreSQL models.py:12. Tests swap in SQLite with StaticPool and a JSONB→JSON compiler hook conftest.py:11–14.
Interview extensionTrade-offs: the ORM gives safety (parameterized queries prevent SQL injection) and speed of development, but makes N+1 query patterns easy to write by accident (they occur here). Missing: Alembic migrations (the schema has drifted between models.py and seed.sql), selectinload/joins for batch loading, composite unique constraints on link tables in the ORM. SQLite in tests is fast but hides PostgreSQL-specific behaviour (JSONB operators, case-sensitivity, concurrency). Testcontainers with real Postgres is more faithful. Alternatives: MongoDB (flexible documents, but this data is highly relational with many-to-many skills), raw SQL with asyncpg (faster, more code), SQLModel (Pydantic + SQLAlchemy in one).

Redis (optional cache)

Core understandingAn in-memory key-value store. It's very fast because data lives in RAM. It is commonly used as a cache: keep the result of an expensive computation for a short time so repeated requests are cheap.
In this repositoryCache-aside on GET /summary: read key job:summary:{id}; on a miss, compute and SETEX for 300 s main.py:912–921 main.py:1014–1016. Invalidated after uploads and rankings for that job. If Redis isn't reachable at import time, all cache calls are no-ops. Compose provides Redis; the Kubernetes manifest does not set REDIS_URL.
Interview extensionStaleness: top_skills is global, so job A's cached summary can go stale when resumes arrive for job B (until the TTL expires). KEYS is O(N) and blocks Redis; prefer DEL for exact keys or SCAN for patterns. Availability check only at import: if Redis comes up later, the process never uses it; if it dies later, calls fail and are caught per call. Alternatives: in-process LRU (functools.lru_cache/cachetools: no network, but per-replica and lost on restart), Memcached (simple, no data structures), HTTP caching with ETags.

JWT (PyJWT, HS256) + bcrypt

Core understandingbcrypt turns a password into a slow, salted, one-way hash, so a stolen database doesn't reveal passwords. A JWT (JSON Web Token) is a signed string header.payload.signature. The server signs it at login; the client sends it back in the Authorization: Bearer header; the server verifies the signature instead of keeping a session table.
In this repositorybcrypt cost 12 (≈270 ms per hash/verify on this sandbox's CPU) auth.py:106–110. JWT payload {user_id, role, name, exp, iat}, HS256 with JWT_SECRET_KEY auth.py:130–140. get_current_user decodes the token and re-loads the user from the DB auth.py:187–205. The frontend stores the token in localStorage Login.jsx:100.
Interview extensionStateless trade-off: you can't revoke a JWT before it expires (24 h here) without a deny-list. localStorage vs HttpOnly cookie: localStorage is readable by any XSS script; an HttpOnly cookie isn't readable by JS but needs CSRF protection. Hard-coded fallback secret: if the env var is missing, anyone who reads the repo can forge tokens. Alternatives: server-side sessions (revocable, needs a store), OAuth2/OIDC with an identity provider (Auth0, Cognito), argon2id for hashing (memory-hard, recommended by OWASP).

Core understandingA pretrained neural network that maps a piece of text to a fixed-length list of numbers (a vector) so that texts with similar meaning land close together. NumPy does fast array math on those vectors.

E.1 Concepts from zero

AI vs ML vs this project

Core understandingAI is the broad goal of making computers do "intelligent" tasks. Machine learning is the subset where behaviour is learned from data rather than hand-written rules. Training adjusts a model's parameters using data; inference uses the finished model to make predictions. Here the "AI" is (a) hand-written rules (regex) and (b) inference with a model someone else trained.
In this repositoryThe rule-based parts are parse_contacts and extract_skills. The learned part is SentenceTransformer("all-MiniLM-L6-v2").encode(...) ml_utils.py:17–18. The scoring weights (0.7/0.3/0.05/0.6) are hand-set constants, not learned ml_utils.py:276–279.
Interview extension"Why not learn the weights?" Because you need labelled outcomes (for example, recruiter shortlist decisions). Embeddings, tokenization and cosine similarity

Core understandingThe model splits text into tokens (word pieces), runs them through a transformer network, and averages the outputs into one vector: here, 384 numbers. Texts about similar things produce vectors pointing in similar directions. Cosine similarity = cos(angle) = (a·b)/(|a||b|): 1 means same direction, 0 means unrelated (orthogonal), −1 means opposite.
In this repositoryencode(..., normalize_embeddings=True) makes |v| = 1, so cosine equals the dot product ml_utils.py:191. The job vector embeds title + description; the resume vector embeds the entire extracted text. Cosine is mapped to [0, 1] by (cos + 1)/2 ml_utils.py:257–259.
Interview extensionThe (cos+1)/2 mapping compresses the useful range. Unrelated texts with cos ≈ 0 already get semantic = 0.5, so everyone gets ≈ 0.15 of the 0.30 weight for free, and the semantic term barely separates candidates. Alternatives: clip negatives (max(0, cos)), min-max normalize within a job, or calibrate on data. Truncation: long resumes exceed the model's max sequence length and the tail is ignored. Chunk the resume, embed each chunk, and take the max or mean similarity. Context window refers to this maximum token count.

E.2 Pipeline trace (input → output)

  1. Input: uploaded bytes → file on disk.
  2. Extraction: extract_text → raw string (no cleaning, no section detection).
  3. Contacts: regex email, NANP-style phone, header-line name heuristic.
  4. Skill detection: vocabulary = every row in skills (seed skills plus every skill any HR has ever typed). Each is regex-searched in the lowercased text. Cost O(|vocab| × |text|).
  5. Embedding: embed_text(raw_text) → 384 floats (or the random fallback) → stored in resumes.embedding.
  6. Scoring (at /summary or /rank): set intersection for skills, cosine for semantics, composite formula, threshold.
  7. Output: JSON per candidate: score, status, matched/missing skills, coverage vector, rendered as charts.

Local vs remote inference: local (in-process, CPU in Docker). There are no API keys and no per-call cost. Costs are RAM (the model plus PyTorch, typically hundreds of MB Inferred), a cold-start download on first use, and CPU time per embed inside the request.

E.3 The fallback embedding (a hidden correctness risk)

If loading the model fails (no internet for the first download, missing package, out of memory), embed_text returns a random unit vector seeded with hash(text[:100]) ml_utils.py:196–200. Problems, all verified Verified by execution:

  • Python's hash() for strings is randomized per process (PYTHONHASHSEED). The same text produced different vectors in two runs, so "deterministic fallback" is false.
  • Random vectors make the semantic term noise centred on 0.5. The ranking silently becomes skill-only plus noise, while the UI still says "semantic match".
  • np.random.seed mutates NumPy's global RNG (a side effect on any other code using it).
  • get_model() retries the import and download on every call after a failure, which adds latency to every request.
  • /readyz does report "fallback_mode", but still returns 200, so orchestrators keep sending traffic main.py:202–207.

Better: fail readiness when the model isn't loaded (or expose a degraded flag), bake the model into the image, use a stable hash (hashlib.sha256) if a deterministic stub is needed in tests, and never mix stub vectors with real ones in one ranking.

E.4 Scoring formula with a worked example

skill_score = |required ∩ found| / |required|          (1.0 if no required skills but candidate has some; 0.5 if both empty)
semantic    = clip((cos(job_vec, resume_vec) + 1) / 2, 0, 1)     (0.5 if either vector is missing)
bonus       = 0.05 if skill_score ≥ 0.70 else 0
final       = min(1.0, 0.70·skill_score + 0.30·semantic + bonus)
status      = "accepted" if final ≥ 0.60 else "rejected"

Reliability characteristics

  • Partial writes: multiple commits per upload; a crash between them leaves inconsistent rows. There's no idempotency key, so a client retry after a timeout creates duplicate resumes.
  • Graceful degradation: Redis down → no cache (fine). Model down → random vectors (silently wrong). DB down at startup → the server still starts and /readyz returns 503 (good for Kubernetes).
  • Timeouts and retries: Axios has a 30 s timeout; the backend has no timeouts around parsing or embedding. A huge PDF can tie up a worker thread.
  • Single process state: the METRICS counters and Redis availability flag are per process, so metrics reset on restart and diverge across replicas or workers. The counters aren't thread-safe for increments from sync handlers (minor race).
  • Cold start: the first embedding request triggers the model download and load, which is slow on a fresh container. The readiness probe also calls get_model().

Bottlenecks in order of impact

  1. Synchronous embedding inside the upload request (CPU-heavy, per file, sequential in batch).
  2. N+1 queries in rank/summary (fix with joins/selectinload or a single aggregate query).
  3. JSON-encoded vectors parsed into Python lists, then into NumPy for every request (store as float arrays or pgvector; cache the matrix).
  4. Skill extraction compiles and runs one regex per vocabulary entry per resume, and the vocabulary grows with every job (use one combined regex, Aho–Corasick, or token-set lookup).
  5. Blocking bcrypt in async def (make the routes def or use run_in_threadpool).

I.2 Algorithms, data structures and complexity

  • Skill overlap: Python set intersection/difference, average O(min(|R|,|C|)). Sets give O(1) membership. Sorted output for stable display.
  • Skill extraction: for V vocabulary skills and text length T, roughly O(V·T) regex scanning per resume. A trie/Aho–Corasick automaton would make it O(T + matches).
  • Vectorized cosine: stacking N vectors of dimension d=384 into an N×d matrix; one matrix-vector product is O(N·d) but executes in optimized BLAS/C. Norms are computed per row. The final ranking sort happens in /summary: O(N log N).
  • Grouping: dict of candidate_id → list of evaluations, then max per group: O(N).
  • Space: matrix N×384 float32 ≈ 1.5 KB per candidate (≈ 15 MB for 10,000).

Detail: improvement #4 (async ingestion) — design sketch
  1. API saves the file to object storage, inserts resumes(status='pending'), enqueues {resume_id}, returns 202.
  2. Worker pool pulls messages, extracts text, embeds in batches of 32–64 with embed_batch, writes skills, sets status='ready', and invalidates the cache.
  3. Failures retry with backoff; after N attempts the item goes to a dead-letter queue with status='failed'.
  4. The UI polls GET /api/resumes/{id} or receives server-sent events.

Trade-off: more moving parts (broker, workers, monitoring) and eventual consistency (the candidate appears on the dashboard a few seconds later). Success metric: upload p95 under 300 ms regardless of file size; ingestion throughput scales linearly with workers.

Q-M3. Explain cosine similarity. Why normalize embeddings? Medium · AI / ML

Q-M4. Why map cosine with (cos + 1)/2? Is that a good idea? Hard · AI / ML

It squeezes [−1,1] into [0,1] so it can be combined with the skill fraction. But real text embeddings rarely go negative, so unrelated texts already get ≈0.5. Everyone receives ≈0.15 of the 0.30 semantic weight, and the useful spread is compressed.

Reasoning & trade-offs

F.5 System-design interview questions (SDE-1 level)

SD-1 · Design a resume-screening platform for many companies

Approach: clarify → requirements → estimates → API → data model → HLD → deep-dive (ingestion, scoring) → bottlenecks → trade-offs.

Requirements: functional (multi-tenant orgs, jobs, applications, scoring, dashboard, secure files); non-functional (tenant isolation, upload ack < 1 s, dashboard p95 < 500 ms, 99.9% availability, privacy compliance).

Architecture: the proposed HLD above. Org-scoped tables (or RLS), object storage for files, queue-based ingestion, pgvector, precomputed scores per application, Redis for cache and rate limits.

Data flow: upload → 202 → worker (parse, skills, embed) → store features → score against the job → write applications.score → invalidate the dashboard cache → recruiter reads precomputed, paginated rankings.

Trade-offs: precompute on write (fast reads, recompute if the job changes) vs compute on read (always fresh, slow at scale); pgvector vs a dedicated vector DB; shared schema + RLS vs DB-per-tenant.

Existing vs proposed: today = single tenant, synchronous, local files, compute-on-read. Everything above beyond that is proposed.

SD-2 · Design a reliable resume-ingestion pipeline

Requirements: at-least-once processing, no duplicates, retries for transient failures, visibility of progress, bounded cost.

Design: API stores the file (content hash as key), inserts resume(status=pending, hash) with a unique index on (org, hash), publishes resume_id. Workers process idempotently (skip if already ready), embed in batches, commit in one transaction, ack the message last. Retries with exponential backoff and jitter; after N attempts → DLQ + status=failed. Metrics: queue depth, age of oldest message, failure rate.

Trade-offs: exactly-once is impractical, so aim for at-least-once delivery plus idempotent consumers. Batching improves throughput but adds latency.

From this repo: reuse extract_text, extract_skills, embed_batch (already written, currently unused by the API).

SD-3 · Design semantic candidate search across all resumes

Design: hybrid retrieval. (1) Filters in SQL (org, location, skills via an inverted index or link table). (2) ANN over embeddings (pgvector HNSW) for the top 200. (3) Exact re-scoring with the composite formula plus explanations. (4) Pagination with a stable sort. Optionally BM25 (Postgres full-text) fused with vector scores (reciprocal rank fusion).

Failure modes: ANN recall below 100%; stale vectors after a model upgrade (store model_version, re-embed in the background).

SD-4 · Design rate limiting for login and upload

Design: token bucket per (IP, route) and per (user, route) in Redis, with an atomic Lua script that refills from a timestamp and decrements. Return 429 + Retry-After. Stricter for /login (e.g. 5/min/IP plus progressive delays per account). Coarse limits also at the edge (Nginx limit_req/WAF).

Trade-offs: fixed window (simple, bursty at edges) vs sliding log (accurate, memory-heavy) vs token bucket (smooth, allows bursts). If Redis is down: fail open (availability) or fail closed (security)? For login, prefer fail-closed with a local fallback limiter.

Today: rate_limit exists but does nothing cache.py:71–81.

SD-5 · Design secure resume storage and download

Design: private bucket, key org/{org_id}/resumes/{uuid}, server-side encryption, an access check in the API (recruiter owns the job), then a pre-signed URL valid for 60 s; audit log entry per download; lifecycle rules for retention and deletion; virus scan on upload (async).

Today: local disk, absolute paths in the DB, unauthenticated sequential-ID download.
