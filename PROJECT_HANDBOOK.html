1.0 Start here: the project explained from zero

In plain words A company posts a job ("we need a Python developer who knows Docker"). Many people send their resumes, and reading all of them takes hours. This app reads the resumes automatically, checks which required skills each person mentions, measures how closely each resume "means the same thing" as the job description, gives every applicant a score from 0 to 100%, and shows the recruiter a ranked list with charts. It runs on a rented Amazon server (AWS EC2) inside Docker containers.

The story of one resume (follow it end to end)

  1. A recruiter posts a job. On the web page they type a title, a description and required skills (for example python, docker, sql). The browser sends this to the server, which saves it in the database.
  2. A candidate applies. They sign up, pick the job and upload a resume file (PDF, Word .docx or plain .txt).
  3. The server checks the file. Is the type allowed? Is it really a PDF and not a renamed program? Is it under 15 MB? Then it saves the file to disk under a random name.
  4. The server reads the file. It pulls out the plain text, finds the name, email and phone number with text patterns, and finds which known skills appear.
  5. The server turns the text into numbers. A small AI model (MiniLM) converts the resume into a list of 384 numbers called an embedding. Texts with similar meaning get similar lists. The job description was converted the same way when it was posted.
  6. Everything is stored in a PostgreSQL database: the applicant, the resume, its skills and its embedding.
  7. The recruiter opens the dashboard. The server scores every resume for that job: 70% from "how many required skills are present", 30% from "how similar the meanings are", plus a small bonus for covering most skills. Scores of 60% or more are labelled Shortlisted.
  8. The recruiter sees ranked cards, missing skills, charts and a side-by-side comparison, and can download the original resume.

What this project is not

It does not train an AI model; it only uses a ready-made one. It does not call ChatGPT or any paid API. Its ranking accuracy has never been measured, because there is no labelled data saying which candidates were truly good. Keep these limits in mind when you talk about it.

Problem it addresses

Recruiters receive many resumes per opening, and reading each one is slow. Plain keyword search misses meaning. This project scores each resume against a job with two cheap, repeatable signals: which required skills appear (keyword matching) and how similar the whole resume is to the job text (sentence embeddings). 1.2 Executive summary & technical summary

In plain language

A recruiter posts a job and lists required skills, for example "python, docker, pytorch". Candidates upload resumes. The server reads the text out of each file, finds the person's name, email and phone with pattern matching, and looks for the job's skills in the text. It also turns both the job description and the resume into a list of 384 numbers that capture meaning (an embedding). The closer two embeddings point in the same direction, the more similar the texts. Each candidate gets a score: 70% from the share of required skills found, 30% from text similarity, and a +0.05 bonus if they cover at least 70% of the skills. Scores of 0.60 or higher are labelled "accepted" (the UI shows "Shortlisted"). The rest are "rejected" (the UI shows "Under Review").

Technically

  • Backend: a FastAPI app with 15 HTTP routes, split into routers/ (HTTP layer), services/ (business logic) and helper modules (main.py:77). It uses SQLAlchemy on PostgreSQL (SQLite in tests), PyJWT bearer tokens with bcrypt password hashes, role and ownership checks on every recruiter route, rate limiting on login and sign-up, and an optional Redis cache Verified by execution.
  • ML: sentence-transformers/all-MiniLM-L6-v2 for inference only (no training, no LLM, no RAG). It loads in a background thread at start-up. Embeddings are stored as JSON arrays in the database, and one NumPy matrix product scores all resumes at once. If the model is not available, the meaning part is scored as a neutral 0.5 and the dashboard says so; "Evaluate Candidates" fills it in later Verified by execution.
  • Frontend: a React 18 single-page app (Vite build, React Router, Axios, Chart.js). Each role downloads only its own screens. The login token is kept in the browser's localStorage Implemented.
  • Quality and operations: 157 pytest tests pass on SQLite and PostgreSQL Verified by execution. Every Python module, class and function has a docstring, enforced by the linter Verified by execution. Docker Compose, Nginx, Kubernetes and Render configs plus a GitHub Actions workflow exist Configured. Production runs with Docker Compose on AWS EC2 Stated by owner.

2-minute version

Problem. Screening many resumes by hand is slow. Keyword search is brittle. Calling an LLM per resume is costly and gives different answers each time.

Design. React SPA → Nginx → FastAPI → PostgreSQL and Redis, as four Docker containers on one EC2 instance. On upload I check the file type by its content signature, stream it to disk with a 15 MB cap and extract text (pypdf / python-docx). I parse contacts with regex and match skills with boundary-aware patterns plus an alias table, so "k8s" counts as Kubernetes but "R&D" doesn't count as R. I compute a 384-dimension MiniLM embedding for the whole batch in one model call and store everything relationally across 8 tables.

Scoring. Skill overlap = matched required skills ÷ required skills. Semantic score = cosine similarity rescaled from [-1, 1] to [0, 1]. Final = min(1, 0.7·skill + 0.3·semantic + 0.05 bonus if skill ≥ 0.7), threshold 0.6. One function does the scoring for both the live dashboard and the saved rankings, using one matrix-vector product for all candidates.

Engineering. JWT plus bcrypt, role and ownership checks on every recruiter route, a rate-limited login that cannot be bypassed with spoofed headers, a Redis cache-aside summary with invalidation, request IDs and Prometheus-style metrics, health and readiness probes, a constant number of SQL queries per dashboard load, and 157 tests running on SQLite and PostgreSQL in CI.

What I'm proud of. I audited my first version, found real security holes (recruiter data reachable without login, a rate limit that could be bypassed), fixed them and wrote tests that prove each exploit now fails.

Honest limits. No labelled dataset, so no accuracy claim. The weights are hand-picked. Upload processing is synchronous, and files live on the server's disk, which limits scaling beyond one machine.

1.5 High-level architecture

How to read the picture: boxes are programs or storage, arrows are requests. In production every box except the browser runs as a Docker container on one AWS EC2 machine Stated by owner.

Primary execution flow in one paragraph

A candidate uploads a file. The resumes router checks the login token, and services/ingestion.py checks the file type and size, streams it to the uploads folder, extracts the text, embeds every file of the request in one model call, and saves the applicant, resume and skill links inside a savepoint (a mini-transaction per file, so one bad file cannot leave half-saved rows). Then it clears the job's cached dashboard. Later the recruiter opens the dashboard. GET /api/jobs/{id}/summary checks that the recruiter owns the job, loads all its resumes with a fixed number of queries, scores them with score_candidates, keeps each applicant's best resume, adds chart data, caches the result in Redis (if available) and returns it. Pressing "Evaluate Candidates" calls POST /rank, which fills in missing embeddings, re-scores everything and saves a snapshot in the rankings table.

B. Architecture and system workflow

What "architecture" means here

Core understandingArchitecture is the set of big parts of a system, what each is responsible for, and how they talk. Think of a restaurant: the dining room (frontend) takes orders, the kitchen (backend) cooks, the pantry (database) stores ingredients, and a recipe book (the ML model) guides how dishes are judged.
In this repositoryA classic three-tier web app: React SPA (presentation) → FastAPI (application logic, layered as routers → services → helpers) → PostgreSQL (data). Redis is an optional side-cache. The ML model runs inside the API process (no separate inference service). Communication is synchronous HTTP/JSON. There are no message queues or background jobs. In production the four parts run as Docker containers on one AWS EC2 machine Stated by owner.
Interview extensionThis is a modular monolith: one deployable service with clear internal layers. Routers know HTTP, services know the business rules and transactions, ml_utils is pure functions. That separation is what made the security fixes easy to test. The in-process model couples API latency and memory to ML inference; at scale you split ingestion into a worker and the model into its own service (section F.4 of Layer 3).

B.1 Startup sequence (what happens on uvicorn app.main:app)

  1. Python imports app.main. app.config reads and validates every setting; an unsafe production config stops here config.py:101–151.
  2. app.db builds the engine (no connection is opened yet) db.py:48. app.models registers the 8 tables and their indexes.
  3. app.ml_utils creates the model holder but does not load the model yet. app.cache creates the Redis holder but does not connect yet.
  4. The FastAPI app is created; middleware and the five routers are registered.
  5. Uvicorn starts and runs lifespan: upload folder, ensure_schema() (creates missing tables, merges duplicate skills; if the database is down it logs and lets /readyz retry) and a background thread that loads the model main.py:33.
  6. The server accepts requests within seconds. /readyz reports when the database and (in production) the model are ready, so a load balancer or Kubernetes only sends traffic then.

B.2 Request lifecycle (generic)

  1. Browser: Axios builds the request; the interceptor adds Authorization: Bearer <token> from the saved session api.js:22.
  2. Proxy: Nginx (Docker/EC2) or the Vite dev server forwards /api/* to the backend on port 8000. Nginx overwrites X-Forwarded-For with the real client address nginx.conf:22.
  3. Middleware: CORS → security headers → tracing (request ID, timer, metrics, crash → JSON 500) observability.py:81–104.
  4. Routing and validation: FastAPI matches the path and parses path, query and form parameters (wrong types → automatic 422).
  5. Dependencies: get_db opens a session; get_current_user checks the token; require_hr checks the role; rate limits apply to login and sign-up.
  6. Handler: the router calls a service; the service reads/writes the database and may call ml_utils. Ordinary def handlers run in a thread pool, so slow work does not block other requests.
  7. Response: the response_model shapes the JSON; the session is closed; errors become {"detail": ...} with the right status code.
  8. Browser: a 401 clears the session and shows the login screen with a message api.js:32.

B.3 End-to-end user journeys

J1 · Register & login
  1. Login.jsx checks the email and password rules locally and sends JSON to /api/register, including access_code when the role is recruiter Login.jsx:96.
  2. The register route is rate limited (5 per minute per IP). _register cleans the name, validates email and password, checks the role, and for recruiters compares the access code in constant time. A duplicate email → 409. The password is hashed with bcrypt in a worker thread and the user is saved auth.py:63–100.
  3. The response is a token (201), so the user is signed in immediately. /api/login (10 per minute per IP) always runs one bcrypt check and returns the same 401 message for an unknown email and a wrong password auth.py:124–138.
  4. The UI saves {token, role, name} through session.js and shows the role's screens.

Error paths: 400 invalid input, 403 wrong/disabled recruiter code, 409 duplicate email, 401 bad login, 429 too many attempts (with Retry-After). The token holds sub, role, name, iat, exp (60 minutes); the role used for decisions is always re-read from the database.

J2 · Recruiter posts a job
  1. UploadJob.jsx sends form data: title, description, comma-joined skills. The owner is not sent; the server takes it from the token UploadJob.jsx:67.
  2. create_job requires a recruiter, validates the title (3–120) and description (20–10,000), and normalises skills (lower case, allowed characters, 1–30 unique) jobs.py:70–75.
  3. It embeds title + description (NULL if the model is not loaded yet), saves the job, and links each skill, creating new vocabulary entries safely if needed.
  4. The UI opens the dashboard with the new job selected.

Worth knowing: every skill a recruiter adds joins the shared vocabulary that future resumes are scanned for.

J3 · Candidate uploads resume(s) — the ingestion pipeline
  1. UploadResume.jsx checks type, size and count locally. One file → POST /api/resumes/upload; several → /batch-upload; a job is required. The progress bar shows real bytes sent, then "processing" useUpload.js:19.
  2. The router checks the token and the job, and rejects batches over 25 files resumes.py:43–47.
  3. save_upload for each file: extension allowed? first bytes match the type? Stream to disk in 64 KB chunks, stop at 15 MB (413), reject empty files. The stored name is <12 random hex>_<original name>, with folder parts removed so paths like ../../x cannot escape ingestion.py:78.
  4. process_uploads: extract text from every file (unreadable or image-only → that file fails and is deleted), then embed all readable texts in one model call ingestion.py:155.
  5. For each resume, inside its own savepoint: decide the applicant (_upsert_candidate: a candidate's upload belongs to their account; a recruiter's upload uses the email in the document), create the resume row, detect skills and link them ingestion.py:163.
  6. One commit for the whole request (if it fails, the stored files are deleted), then the job's cached dashboard is cleared. The response lists every file in order with processed or failed and a reason.

D2. Data model and persistence

In plain wordsThe database is a set of tables, like spreadsheets that point at each other. Each row has an ID (the primary key, PK). A foreign key (FK) is a column that stores another table's ID, which is how a resume "knows" its job. A unique constraint makes the database itself refuse duplicates. An index is like a book index: it makes lookups fast. A transaction groups several changes so they are saved all together or not at all.

E. AI / ML pipeline

Precise classification (say it this way in interviews) This project uses a pretrained transformer embedding model for inference (semantic similarity) combined with rule-based NLP (regular-expression extraction). It does not train or fine-tune any model, does not use a large language model or generative AI, does not implement RAG, and has no evaluation dataset or accuracy metrics.

E.1 Concepts from zero

AI vs ML vs this project

Core understandingAI is the broad goal of making computers do "intelligent" tasks. Machine learning is the subset where behaviour is learned from data rather than hand-written rules. Training adjusts a model's parameters using data; inference uses the finished model to make predictions. Here the "AI" is (a) hand-written rules (regex) and (b) inference with a model someone else trained.
In this repositoryThe rule-based parts are parse_contacts and extract_skills. The learned part is the sentence-transformer model all-MiniLM-L6-v2, held by one _EmbeddingModel object ml_utils.py:51–99. The scoring weights are named constants chosen by hand, not learned ml_utils.py:34–39.
Interview extension"Why not learn the weights?" Because you need labelled outcomes (for example, recruiter shortlist decisions). With those you could fit logistic regression on [skill_score, semantic, …] or a learning-to-rank model (LambdaMART), and evaluate with precision@k, NDCG and AUC. Watch for bias: historical hiring labels encode past bias.

Embeddings, tokenization and cosine similarity

Core understandingThe model splits text into tokens (word pieces), runs them through a transformer network, and averages the outputs into one vector: here, 384 numbers. Think of it as GPS coordinates for meaning: texts about similar things land close together. Cosine similarity = cos(angle) = (a·b)/(|a||b|): 1 means same direction, 0 means unrelated, −1 means opposite.
In this repositoryencode(..., normalize_embeddings=True) makes every vector length 1 ml_utils.py:133. All resumes of a job are compared with the job in one matrix-vector multiplication (NumPy), then mapped to [0, 1] with (cos + 1)/2 ml_utils.py:426–443. The job vector embeds title + description; the resume vector embeds the extracted text.
Interview extensionThe (cos+1)/2 mapping compresses the useful range: unrelated texts with cos ≈ 0 already get 0.5, so everyone gets ≈ 0.15 of the 0.30 weight for free. Alternatives: clip negatives (max(0, cos)), min-max normalise within a job, or calibrate on data. Truncation: MiniLM only reads the beginning of long inputs (its maximum sequence length, also called the context window), so a long resume is embedded mostly from its first part (noted in docs/ARCHITECTURE.md). Fix: split into chunks, embed each, take the max or mean similarity Proposed.

E.2 Pipeline trace (input → output)

  1. Input: uploaded bytes are streamed to disk under a random name; extension, "magic bytes" (file signature) and 15 MB size are checked first ingestion.py:64–96.
  2. Extraction: extract_text reads PDF (also owner-password-only PDFs), DOCX (headers, footers, body, tables) or TXT (UTF-16, then UTF-8, cp1252, latin-1) ml_utils.py:231–252. Fewer than 30 readable characters → "failed" (scanned image PDFs have no text layer).
  3. Contacts: regex email; international phone formats (but not year ranges like "2018 - 2023"); a name heuristic that skips headings like "Curriculum Vitae" and keeps accents ("José García").
  4. Skill detection: vocabulary = every row in skills. Each skill is normalised ("Machine-Learning" → "machine learning"), then searched with word-boundary rules; known aliases ("k8s" → kubernetes) and special rules for the risky short names R, C and Go ml_utils.py:393–412. Confidence: 0.95 exact, 0.9 special rule, 0.85 alias.
  5. Embedding: all readable files in the request are embedded in one model call (ml_utils.py:114–138). If the model isn't loaded, the result is None (stored as NULL), never a made-up vector.
  6. Saving: candidate, resume and skill links are saved in one transaction (D2); the job's cached summary is cleared.
  7. Scoring (at /summary, cached for 300 s, or at /rank): skill overlap + cosine + bonus → threshold, by the single function score_candidates ml_utils.py:446–447.
  8. Output: JSON per candidate: score, status, matched/missing skills, coverage vector; drawn as cards and charts.

Local vs remote inference: local (in-process, on the CPU, inside the backend container). No API keys and no per-call cost. The Docker image downloads the model while it is being built, so containers on EC2 start without internet access to Hugging Face Dockerfile:18. Costs are RAM (model plus PyTorch, the main reason the EC2 guide asks for at least 4 GB) and CPU time per upload.

E.3 When the model is missing: neutral 0.5 (fixed in v3) Fixed in v3

Before: if the model failed to load, embed_text returned a random vector seeded with Python's hash(). That hash changes every time the process starts, so the "semantic" score was noise that looked real, it changed NumPy's global random state, and the import was retried on every request Verified by execution.

Now:

  • The model loads once, in a background thread at start-up. If loading fails, it is retried at most every 300 seconds, not on every request (double-checked locking keeps it thread-safe).
  • A missing embedding is stored as NULL and scored as a neutral 0.5, which neither helps nor hurts anyone ml_utils.py:39.
  • The summary says so honestly: semantic_available: false, and the dashboard shows a notice.
  • Clicking Evaluate (/rank) fills in missing embeddings once the model is available ranking.py:134–148.
  • /readyz returns 503 until the model is loaded when REQUIRE_EMBEDDING_MODEL is on (the default in production), so a load balancer won't send traffic to a half-ready server.

E.4 Scoring formula with a worked example

skill_score = |required ∩ found| / |required|               (0.5 if the job lists no skills; jobs must list ≥ 1 today)
semantic    = clip((cos(job_vec, resume_vec) + 1) / 2, 0, 1)  (0.5 if either vector is missing)
bonus       = 0.05 if skill_score ≥ 0.70 else 0
final       = min(1.0, 0.70·skill_score + 0.30·semantic + bonus)
status      = "accepted" (Shortlisted) if final ≥ 0.60 else "rejected" (Under review)

Safeguards in place now

Reliability characteristics

  • Atomic writes: one commit per upload batch with a savepoint per file; files on disk are cleaned up if the commit fails. There is still no idempotency key, so a client retry after a timeout can create a duplicate resume.
  • Graceful degradation: Redis down → no cache and in-memory rate limits (quietly, with a 30 s reconnect back-off). Model down → neutral 0.5 and an honest flag; in production /readyz stays 503. Database down at start-up → the app starts, /readyz reports 503 and retries table creation.
  • Timeouts: Axios 120 s and Nginx proxy_read_timeout 300s for big batches; the backend has no time limit around a single slow PDF.
  • Per-process state: metrics counters (now thread-safe) and in-memory rate limits reset on restart and are not shared between processes; Redis-backed limits are shared.
  • Cold start: the model loads in a background thread at start-up (seconds), so the first request isn't stuck waiting for it.

Bottlenecks in order of impact (today)

  1. Text extraction and embedding happen inside the upload request (batched into one model call, but still synchronous). A queue + worker would return immediately.
  2. /rank inserts one row per resume. A bulk insert (one statement) would make it constant.
  3. Vectors stored as JSON are parsed on every uncached summary (the 300 s cache hides most of it); pgvector or binary arrays would be cheaper.
  4. Skill extraction runs one compiled regex per vocabulary skill: O(V·T). One combined pattern or Aho–Corasick would scale better as the vocabulary grows.
  5. One EC2 instance: CPU for embeddings and the database share the same machine.

I.2 Algorithms, data structures and complexity

  • Skill overlap: Python set intersection/difference, average O(min(|R|,|C|)), O(1) membership checks.

  • Best resume per candidate: one pass with a dict: O(N). Sorting: O(N log N), ties broken by resume ID so the order is stable.
  • Space: N×384 float32 ≈ 1.5 KB per candidate (≈ 15 MB for 10,000).

Detail: improvement #3 (async ingestion) — design sketch
  1. API saves the file to object storage, inserts resumes(status='pending'), enqueues {resume_id}, returns 202 Accepted.
  2. Worker pool pulls messages, extracts text, embeds in batches of 32–64 with embed_batch, writes skills, sets status='ready', and clears the cache.
  3. Failures retry with back-off; after N attempts the item goes to a dead-letter queue with status='failed'.
  4. The UI polls GET /api/resumes/{id} or receives server-sent events.

Trade-off: more moving parts (broker, workers, monitoring) and eventual consistency (the candidate appears a few seconds later). Success metric: upload p95 under 300 ms regardless of file size; ingestion throughput grows with the number of workers.

Q-M1. What is an embedding? Easy · AI / ML
Direct answer

A list of numbers that represents the meaning of a text, produced by a neural network. Texts with similar meaning get vectors pointing in similar directions. Here every job (title + description) and every resume becomes 384 numbers; the cosine of the angle between job and resume vectors is the "semantic" part of the composite score (see E.4).

Foundation

Analogy: GPS coordinates for meaning. "Python developer" and "Django engineer" land close together; "Python developer" and "pastry chef" land far apart.

Q-M3. Explain cosine similarity. Why normalize embeddings? Medium · AI / ML
Direct answer

Cosine similarity = (a·b)/(|a||b|), the cosine of the angle between two vectors: 1 same direction, 0 unrelated, −1 opposite. If every vector has length 1 (normalised), the cosine is just the dot product, which is cheap, and long texts don't win just by having bigger vectors.

Evidence in the code

ml_utils.py:133 · ml_utils.py:426–443

Q-M4. Why map cosine with (cos + 1)/2? Is that a good idea? Hard · AI / ML
Direct answer

It squeezes [−1, 1] into [0, 1] so it can be mixed with the skill score. But real text pairs rarely go negative, so unrelated texts already get about 0.5: everyone receives ≈ 0.15 of the 0.30 weight for free, and the semantic term barely separates candidates.

Evidence in the code

ml_utils.py:442

Reasoning & trade-offs

Alternatives: max(0, cos), min-max normalisation within a job, or calibration on labelled data (e.g. logistic regression on cos).

Q-S10. Tell me about the X-Forwarded-For rate-limit bypass. Hard · Security
Direct answer

Behind a proxy, the API learns the client IP from the X-Forwarded-For header. F.4 Scaling and failure scenarios

Capacity estimate (assumptions stated, calculations shown)

Assumptions (illustrative, not measured): 200 companies × 20 open jobs = 4,000 jobs; 300 applicants per job per month; average file 100 KB; each job's dashboard viewed 10 times a day; peak = 10× average.

F.5 System-design interview questions (SDE-1 level)

SD-1 · Design a resume-screening platform for many companies

Approach: clarify → requirements → estimates → API → data model → HLD → deep-dive (ingestion, scoring) → bottlenecks → trade-offs.

Requirements: functional (multi-tenant orgs, jobs, applications, scoring, dashboard, secure files); non-functional (tenant isolation, upload ack < 1 s, dashboard p95 < 500 ms, 99.9% availability, privacy compliance).

Architecture: the proposed HLD above. Org-scoped tables (or RLS), object storage for files, queue-based ingestion, pgvector, precomputed scores per application, Redis for cache and rate limits.

Data flow: upload → 202 → worker (parse, skills, embed) → store features → score against the job → write applications.score → invalidate the dashboard cache → recruiter reads precomputed, paginated rankings.

Trade-offs: precompute on write (fast reads, recompute if the job changes) vs compute on read (always fresh, slow at scale); pgvector vs a dedicated vector DB; shared schema + RLS vs DB-per-tenant.

Existing vs proposed: today = one EC2 instance, single organisation with per-recruiter ownership, synchronous ingestion, files in a Docker volume, compute-on-read with a cache plus saved snapshots. Everything above beyond that is proposed.

SD-2 · Design a reliable resume-ingestion pipeline

Requirements: at-least-once processing, no duplicates, retries for transient failures, visibility of progress, bounded cost.

Design: API stores the file (content hash as key), inserts resume(status=pending, hash) with a unique index on (org, hash), publishes resume_id. Workers process idempotently (skip if already ready), embed in batches, commit in one transaction, ack the message last. Retries with exponential backoff and jitter; after N attempts → DLQ + status=failed. Metrics: queue depth, age of oldest message, failure rate.

Trade-offs: exactly-once is impractical, so aim for at-least-once delivery plus idempotent consumers. Batching improves throughput but adds latency.

From this repo: the worker can reuse process_uploads almost as is: it already embeds a batch in one call, uses a savepoint per file and commits once.

SD-3 · Design semantic candidate search across all resumes

Design: hybrid retrieval. (1) Filters in SQL (org, location, skills via an inverted index or link table). (2) ANN over embeddings (pgvector HNSW) for the top 200. (3) Exact re-scoring with the composite formula plus explanations. (4) Pagination with a stable sort. Optionally BM25 (Postgres full-text) fused with vector scores (reciprocal rank fusion).

Failure modes: ANN recall below 100%; stale vectors after a model upgrade (store model_version, re-embed in the background).

SD-4 · Design rate limiting for login and upload

Design: token bucket per (IP, route) and per (user, route) in Redis, with an atomic Lua script that refills from a timestamp and decrements. Return 429 + Retry-After. Stricter for /login (e.g. 5/min/IP plus progressive delays per account). Coarse limits also at the edge (Nginx limit_req/WAF).

Trade-offs: fixed window (simple, bursty at edges) vs sliding log (accurate, memory-heavy) vs token bucket (smooth, allows bursts). If Redis is down: fail open (availability) or fail closed (security)? For login, prefer fail-closed with a local fallback limiter.

Today: a fixed window per IP in Redis (INCR + EXPIRE) or memory, on login and register, with proxy headers trusted only from private networks rate_limit.py:17. If Redis is down it falls back to per-process counters (fail-open across instances, still limited per process).

SD-5 · Design secure resume storage and download

Design: private bucket, key org/{org_id}/resumes/{uuid}, server-side encryption, an access check in the API (recruiter owns the job), then a pre-signed URL valid for 60 s; audit log entry per download; lifecycle rules for retention and deletion; virus scan on upload (async).

Today: files in a Docker volume on the EC2 disk, relative paths in the DB, download only for the owning recruiter, served through the API with the token. Before v3 anyone could download any resume by counting IDs.

SD-6 · What would you monitor, and what alerts would you set?

RED metrics per route (rate, errors, duration histograms), USE for resources (CPU, memory, DB connections), plus business metrics: resumes ingested/min, failed ingestions, model fallback count (should be 0), cache hit ratio, queue depth/age. Alerts on SLO burn rate (e.g. 5xx > 1% for 10 min), p95 latency, queue age > 5 min, any fallback-mode embedding. Structured logs carry the request ID; traces span API → DB → worker.

Today: request counts and latency sums per route template, cache hits/misses and model status at /metrics (on the instance only), request IDs in logs; no histograms, dashboards or alerts ops.py:60–62. On AWS: CloudWatch agent for logs and an alarm on the ALB//readyz health.
